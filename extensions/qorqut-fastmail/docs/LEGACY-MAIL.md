# Legacy mail records: ownership and transition

## Ownership

Before v1.3.2 the host core kept a per-Project mailbox model in twelve `email_*` tables (mailboxes, conversations, messages,
routing history, history outbox/deliveries, account thread controls and comments, owned folders, thread controls, comments and
decisions), plus history triggers and a Signoff snapshot view. Core no longer owns any of it: a fresh core-only composition
contains no `email_*` table, trigger, view or setting, and the optional provider adds none either.

The exact legacy definitions are now owned by this package as an **offline archive schema** (`qorqut_fastmail.legacy`). They
describe records for reading and export; they are never installed into a running host, and nothing here creates, alters or
drops a table of a live instance. This is deliberate: a live provider with no per-Project mail model has no use for those
tables, and installing them would reintroduce the coupling being retired. `qorqut_fastmail.legacy.LEGACY_DDL` is the original
shape (with its references to `businesses`, `principals`, `signoffs`); `ARCHIVE_DDL` is the same shape for a standalone file,
where those three core references remain plain identifiers and every reference between the mail tables is kept.

Not preserved by the archive: the history triggers and the Signoff snapshot view. They derived data from the tables and from the
generic Signoff history, and they referenced core internals.

## Offline export

The export preserves the raw legacy mail records and their identifiers, as described below. It is **not** an instance migration: it
does not make a pre-v1.3.2 instance openable by the new core, a fresh core does not load the archive or reconstruct imported mail
links (a saved relationship or note reference to a mail item that cannot be resolved is omitted or returned as unavailable), and
no live legacy table, permission bypass or placeholder exists. Moving the rest of an existing instance is a separate real-data
migration.

```
python -m qorqut_fastmail.export COPY_OF_LEGACY_DATABASE.sqlite3 NEW_EXPORT_DIRECTORY [--no-archive]
```

- The source must be a **copy** of an instance database taken while the instance was stopped or drained and checkpointed. It is
  opened read-only and immutable, is hashed before and after, and is refused if a `-wal`/`-journal` file with content sits beside
  it or if it changed during the export. It is never written.
- The target must not exist. The export is built in `NEW_EXPORT_DIRECTORY.partial` and moved into place only after verification.
- Output: `manifest.json`, `tables/<table>.jsonl`, `related/<name>.jsonl`, and `archive.sqlite3` (omit with `--no-archive`).
- Every row and identifier is copied verbatim with its SQLite type (BLOBs as `{"$blob": base64}`). Nothing is dropped, renamed
  or merged. The archive is read back and compared with the JSONL files; AUTOINCREMENT counters, including gaps, are kept.
- Related generic rows are exported next to the mail records: Signoffs linked from `email_decisions` and
  `email_conversations.pending_signoff_id` or whose change set names the retired `email.send` tool; owner conversations with
  `source_type = 'email'` with their messages and read marks; background jobs whose kind starts with `email.`.
- Findings in the source (rows that already violate an internal reference) are reported in the manifest and by exit status 1
  (`needs_review`), never repaired. A database with none of the legacy mail tables is refused (exit status 2) rather than
  reported as an empty success; an all-empty legacy database is reported with `"empty": true`. A table whose columns differ from
  the legacy shape is refused rather than guessed.

The tool is tested only on synthetic databases generated by the tests. It has not been run against a real instance.

## What a live upgrade still needs (not done here)

No migration was run against any real instance. Before upgrading an instance that holds legacy mail data an operator must:

1. Quiesce and drain the instance (queued or approved legacy `email.*` jobs and Signoffs approved under the retired mail
   grant cannot run after the upgrade).
2. Take a checkpointed copy of the database and run the export above; keep the output with the pre-upgrade backup.
3. Expect the new core to refuse to open the existing database at all: it opens only a store whose recorded target identity and
   schema inventory are exactly its own composition, and "no conversion is performed". A database that still holds the `email_*`
   tables, history triggers or Signoff snapshot view fails that check ("unexpected table/trigger/view ..."). Moving the
   non-mail data of an existing instance into a store of the new target is a separate conversion step that this work does not
   provide and has not run; the export above exists so the mail records are not lost when that step is taken.
4. Re-grant agents pinned to Email Management v2 with v3, and select this extension (with `engine_url` and `admin_token_file`)
   if the Fastmail operations are wanted.
