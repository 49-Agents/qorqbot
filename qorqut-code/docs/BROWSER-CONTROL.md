# Explicit Chrome control

Global agents whose role selects the `browser-control` procedure (Ordubashy, Learning
Applier and the permanent workers) use it; browser use itself needs an authorized `browser_turn`
operation, which a permanent worker has only when Ordubashy grants it. Its short native
skill description is discoverable in Claude Code and Codex; the body is read only
for an explicit owner request to use Chrome/the qocaat browser. A URL, ordinary
research or a single web request is insufficient. This is a semantic instruction,
not a keyword hook or a guarantee enforced by code. It supports natural-language
requests without requiring a slash command. Nothing attaches during bootstrap.

The normal integration retains only the existing Qorqut MCP server. Browser
instructions, page snapshots and CLI help are absent from mandatory context.
The pinned `agent-browser` 0.38.1 supplies the actions (see
[AGENT-BROWSER-BACKEND.md](AGENT-BROWSER-BACKEND.md)); it replaced the Playwright CLI
named in some older paragraphs below. Qorqut supplies target selection and
conservative lifecycle handling.
Role artifacts remain procedure-only; executable code lives in core, consistent
with the catalog's prohibition on executable skill files.

## Runtime contract

Under the former Playwright CLI, Qorqut's `browser_init.cjs` (loaded through
Playwright's `browser.initPage` configuration) bounded each tab-title lookup to
750 ms. `agent-browser` does not load it: the generated configuration is empty.
The file is still packaged.

Preparation creates `.qorqut/browser` only when the selected Ordubashy artifact
contains `browser-control`. Invoke it as `sh .qorqut/browser <command>` from the
registered agent workspace. It uses the installation's prepared Python runtime,
so no shell activation or global CLI installation is needed. Re-preparation after
removing the skill/role removes the managed launcher and both native skill copies.

The launcher reads `.qorqut/browser.json` in that exact agent workspace. For Ordubashy and the permanent workers
`agent_browser_manage` writes it, naming the Shared browser, and replaces a hand-written one
([BROWSER-MANAGEMENT.md](BROWSER-MANAGEMENT.md)); for any other agent the operator supplies it:

```json
{
  "schema_version": 1,
  "cdp_endpoint": "http://127.0.0.1:9225",
  "runtime_dir": "/absolute/path/to/deployed/core/tools/browser"
}
```

There is no default endpoint and no fallback browser. Only explicit loopback HTTP
endpoints are accepted. `runtime_dir` is an absolute path: either the runtime
directory with the checked-in npm package and lockfile (`tools/browser`, which pins
`agent-browser` 0.38.1 and needs Node 24 or later; see
[AGENT-BROWSER-BACKEND.md](AGENT-BROWSER-BACKEND.md)), or an installed
`agent-browser` executable. The launcher checks that the runtime supports the
scoped command contract and never downloads packages at invocation. The one
optional entry is `"shared": true`, written only for the Shared browser (see
[browser management](BROWSER-MANAGEMENT.md#how-agents-use-it)).

This file is deployment configuration, not an operational table or role artifact.
Preparation leaves it untouched. Keep it under the existing protected `.qorqut/`
folder. It contains no profile credentials. An agent's file is normally
generated by `agent_browser_manage` and names the Shared browser
(see `BROWSER-MANAGEMENT.md`); a hand-installed file is never replaced by it.

Session identity is derived from the absolute workspace, endpoint and target instance. Commands
run in `work/browser/<session>/`; use absolute paths for file arguments. Artifacts
can contain private page content and remain in that agent's work folder. Ambient
`PLAYWRIGHT_*`, `AGENT_BROWSER_*` and `AI_GATEWAY_*` environment variables are removed.
Each command gets an explicit, empty generated config (`agent-browser.json`). Commands
are serialized with a nonblocking per-session lock and a 45-second outer timeout.
An action timeout is an uncertain outcome; inspect before retrying a submission.

The launcher rejects target/config/session overrides, browser launching, global
shutdown and profile clearing. `detach` preserves the attached browser. Ordinary
page commands, including `type`, `frame` and `eval`, remain available for requested work;
`run-code` is not exposed.
These restrictions prevent common accidents; arbitrary code and processes under
the same OS account can bypass them. They are not an authorization sandbox or
Qorqut's prepared-change/signoff mechanism. The skill respects authorization
already supplied by the owner and requests missing authority before external acts.
Concurrent owner/agent workflows still need coordination; command serialization
does not reserve a browser for a whole conversation.

## Targeted observations

After attaching, `observe` projects the current accessibility snapshot into a
small JSON result while retaining the complete `agent-browser` snapshot as a private
artifact. Use `observe overview`, `observe find "text"`, `observe region
"label"`, `observe values` or `observe table "label"`. `overview` defaults to a
4,000-character response budget; `--budget=<characters>` accepts 1,000 through
24,000 characters, and `--depth=<n>` adjusts its structural scope. The result
keeps actionable accessibility refs, names, values and control state. Dialogs,
alerts, statuses and invalid controls remain visible when a scope is narrow.

The result includes an `observation` handle, `items`, `omitted`, `excluded`,
`next`, `evidence` and a `budget` record. Items are kept whole; when the budget
does not fit another item, `omitted_reason` points to the evidence artifact
instead of silently cutting a result. Continue with the same immutable handle,
for example `observe overview --observation=<handle> --offset=<next>`. Pagination
reads the saved artifact and does not issue another browser command. The
`evidence` path is relative to the workspace's `work/browser/<session>/`
directory; it is mode 0600 and is available when the exact snapshot is needed.
If the first item cannot fit even by itself, `pagination_stalled` and
`oversized_item` explain that there is no advancing `next`; inspect `evidence`
or retry with a larger budget.

Observation failures return a bounded JSON error with an `exit_code` and an
`error_artifact` path containing the complete captured CLI output. The wrapper
rejects arbitrary observation paths and refuses symlinks, non-regular files,
changed evidence and oversized artifacts. This read-only projection does not
add deltas, and uses the same session lock, target selection,
lease and owner activity handling as the existing commands.

As a synthetic size check, a 200-row accessibility snapshot measured 26,584
characters in the existing full snapshot and 3,961 characters in the default
overview response (about 85% fewer characters). These are local character
measurements, not provider-token billing or live-browser benchmarks; small
pages can be larger because the compact JSON carries refs and evidence handles.

## Command vocabulary

The launcher drives the pinned agent-browser 0.38.1 (see [AGENT-BROWSER-BACKEND.md](AGENT-BROWSER-BACKEND.md); the
paragraphs above that name the Playwright CLI are older). It accepts the words an agent is likely to send, whether they
are the launcher's own or the tool's, and turns them into the tool's commands in `qorqut/bootstrap/agent_browser.py`.
`validate_arguments` in `qorqut/bootstrap/browser.py` runs that same translation without running anything, so a command
that cannot run is refused before it starts, on every path that calls it.

| Sent | Becomes |
| --- | --- |
| `read` | A batch of `get url`, `get title` and the tool's `read` of the page the tab shows. The reply is `Address:`, `Title:` and the readable text, in at most 4,000 characters in all; `--budget=N` takes 1,000 to 24,000. `--filter <text>` and `--outline` pass through. When the text is cut, the reply says by how much and how to get more. |
| `open <url>`, `goto <url>` | `open <url>` |
| `type <text>`, `keyboard type <text>` | `keyboard type <text>`: one argument, typed into the focused field |
| `tab`, `tab list`, `tab new [url]`, `tab close [id]`, `tab <id>` | `tab-list`, `tab-new`, `tab-close`, `tab-select`, which are the same commands |
| `back`, `forward` | `go-back`, `go-forward` |
| `snapshot -s <selector>` | `snapshot --selector <selector>`; the other snapshot options are `-i`/`--interactive`, `-c`/`--compact`, `-d <n>`/`--depth <n>`, `--delta` and `--full`. `-c` is always sent. |
| `find <locator> <value> <action> [text]` | Passed through. Locators `role`, `text`, `label`, `placeholder`, `alt`, `title`, `testid`, `first <css>`, `last <css>`, `nth <n> <css>`; actions `click`, `fill <text>`, `check`, `hover`, `text`; options `--name <name>` (role only) and `--exact`. `find <text>` alone still reads the matching text. |
| `scroll [up\|down\|left\|right] [pixels] [--selector <sel>]` | Passed through; `scroll 500` means `scroll down 500` |
| `focus <ref or selector>` | Passed through |
| `wait <ms>`, `wait <selector>`, `wait --text <t>`, `wait --url <pattern>`, `wait --load <state>`, `wait --fn <expression>` | Passed through. A time is at most 30,000 ms, so the wait ends inside the 45-second limit of a command. A wait for a selector or text that never comes ends by itself after 25 seconds. |
| `get url`, `get title`, `get text <sel>`, `get value <sel>`, `get attr <sel> <name>`, `get count <sel>` | Passed through |
| `frame <ref or selector>`, `frame main` | Passed through: enter a frame, or go back to the page |
| `upload <ref or selector> <file>...` | Passed through, each file by the path the browser can open it at; see Uploads below |
| `dialog accept [text]`, `dialog dismiss` | `dialog-accept`, `dialog-dismiss` |
| `eval <function>` | The function is called, as before |
| `eval <expression or statements>` | Run as written; the value of the last statement is printed |

A snapshot ref (`e12`) is sent as `@e12` to `click`, `fill`, `focus`, `get text`, `get value`, `get attr`, `frame` and the
like. `wait`, `get count`, `snapshot --selector` and the selectors of `find first`, `last` and `nth` take CSS only, and a
ref given there is refused with that sentence instead of waiting for it.

A refusal says what to send instead. A word near a supported command names it ("Did you mean 'click'?"). A command of
the tool that is closed on purpose is called that: browser start and stop (`launch`, `quit`, `kill`, `install`),
`connect` and `close` (use `attach` and `detach`, which leave Chrome running), `cookies`, `storage`, `network`, `set`
(use `resize <width> <height>`), `mouse`, `clipboard`, `download` and `wait --download`. Also closed: `get cdp-url`,
which would hand out the browser's connection address; `get html`, `box` and `styles` (use `eval`); and `read <url>`,
because a read by address is fetched over HTTP outside the browser's own session (send `goto <url>`, then `read`).

Options are checked per command against a table. An argument that begins with `-` and is not in the command's table is
refused in every position, including after the positional arguments, as the value of another option and in the
`--option=value` form, so `--session`, `--cdp`, `--config`, `--profile` and the rest of the tool's lifecycle options
cannot be added to any command. This also means a text argument cannot begin with `-`; the refusal says so. The tool
ignores the `=` form of `--name` and `--selector` and falls back to its default (the first match, the whole page), so
the launcher sends every `--option=value` as `--option value`.

Two refusals protect against a silent wrong result. `type` takes one text argument: the tool's own `type <selector>
<text>` would type "e5 text" into whatever has focus. `find <locator> <value>` needs an action, because the tool would
click.

Uploads. The tool gives Chrome the path of each file, not its content, and Chrome opens the file itself. Chrome accepts
a path it cannot open: the page then gets a file of that name with 0 bytes whose reading fails (`NotFoundError`), and
the tool still prints "Done". A managed Chrome runs outside the application service's mount namespace (see
[BROWSER-MANAGEMENT.md](BROWSER-MANAGEMENT.md)), so where the service sees its instance through a private bind mount
(`BindPaths=`), every path below that mount was such a path. `upload_arguments` in `qorqut/bootstrap/browser.py`
therefore sends each file by the path it has on the underlying filesystem (`outside_private_mounts`, the translation
the browser's own folders use), after following links in the folder's path; the file's name, which the page sees, is
kept. A file that does not exist is refused before anything reaches the page, and `upload` without a file is refused
by `validate_arguments`. A relative path is read from the tool's working folder. A file that has no path where Chrome
runs, such as one under a temporary folder private to the service, still arrives empty. Checked on 2026-11-22 with the
command run inside a mount namespace and a throwaway Chrome outside it: before, the page got the file's name with
0 bytes; now it reads the whole file.

Frames. Fields inside a frame are in `snapshot` with refs of their own, and `fill` and `click` reach them directly.
`frame <css>` enters only a frame of the same site; for a frame of another site the tool answers "Frame not found".
Stripe marks its card frame `role=presentation`, so `snapshot` leaves it out. Removing that mark with `eval`
(`document.querySelectorAll('iframe[role=presentation]').forEach(f => f.removeAttribute('role'))`) makes the next
`snapshot` show the frame's fields with refs. When `frame` fails with "Frame not found", `frame_advice` in
`agent_browser.py` appends these steps to the error. Both browser skills say the same.

What the pinned tool does, found against a throwaway headless Chrome on 2026-11-19:

* `find ... click` on a name that matches several elements does not refuse: it takes the first match in page order and
  prints "Done". `--exact` (or `find role button click --name <exact name>`) and a ref avoid this. `find role button
  text --name X` for a name that matches nothing lists the names it saw.
* `eval` runs an expression as written (`document.title`), and runs several statements, printing the last value. A
  top-level `return` is a syntax error, and a top-level `const` or `let` stays in the page, so sending the same
  `const x = 1` twice fails the second time: use `var` or a function. A function that is not called prints `{}`.
* `read` without an address prints only the text; it carries neither the address nor the title, which is why the
  launcher asks for all three in one batch.
* `wait` reads `+2000` and `02000` as a time, which is why a time is checked in every form that starts like a number.

## qocaat finding and rollout

On 2026-09-11 the existing `remote-browser.service` was active and exposed Chrome
153.0.8010.36 at loopback port 9225. Raw CDP responded, but an existing page had
an empty URL. Playwright's initial-page initialization waits for that page's first
navigation, explaining the earlier attachment timeout. The launcher checks CDP
target metadata before attaching and reports this exact condition without
navigating, closing or resetting owner tabs. `about:blank` is valid; an empty
string or `:` is not. The owner can navigate the affected tab to `about:blank`
before retrying. Do not restart Chrome or discard its profile as an automatic fix.

Unlike a bare `connectOverCDP()` probe, CLI 0.1.19's CDP factory passes
`noDefaults: true`. It preserves Chrome's default download/display settings.
No patch to Playwright or the machine's `/opt/remote-browser` runtime is needed.

After the owner approves merging/releasing both repositories:

1. Install the locked CLI dependencies in the deployed core release.
2. Publish Ordubashy 1.15.1, explicitly repin the intended Ordubashy profile while
   preserving plugins, grants, scope and assignments, and re-prepare it with the
   deployed core interpreter. Publishing source does not update live pins.
3. Install the target JSON above only in the intended Ordubashy workspace, using
   the actual deployed runtime path. Do not copy it to other agents.
4. Verify the prepared launcher with `sh .qorqut/browser --help`. In an
   owner-requested Chrome task, attach, inspect tabs, and detach. Resolve the
   empty-URL tab through the owner if it still exists. Do not use an owner's real
   agent conversation as an automated model acceptance test.

Rollback: detach the selected CLI session, restore the previous role pin and
re-prepare. The managed launcher/skill disappear. Retain operator target config,
work artifacts and Chrome profile for recovery; no browser data migration exists.

## The captcha command

An agent that sees a captcha sends `["captcha"]` as a `browser_turn` command, with nothing else: no key, no site key, no
selector. Its skill says so in one line. It goes in a call of its own: inside `commands` it is refused before anything
runs. Being a command, it goes through the same authorization, handle, browser
selection, use lock and per-session command lock as `click`; `qorqut/browser/access.py` hands it to
`qorqut/browser/captcha.py` instead of `agent-browser`. The shell launcher does not have it.

The server works on the tab the caller's session is bound to (read from `agent-browser`'s `<session>.target` file, as the
idle-tab sweeper does), over Chrome's loopback DevTools port:

1. **Find.** The tab's frames are listed, frames of other sites included. reCAPTCHA v2, hCaptcha and Cloudflare Turnstile
   are recognised by their frame's address (by path, so a proxied or stand-in widget is recognised too); the site key is
   read from that address, or from the page's `data-sitekey`. reCAPTCHA v3 is recognised by the script the page loads,
   Cloudflare's own "checking your browser" page by its markup. A widget with a checkbox is chosen before an invisible
   one, and any widget before reCAPTCHA v3.
2. **Click.** A widget with a checkbox is scrolled into view and gets a real mouse click on the checkbox (its place is
   read inside the widget's frame; Turnstile hides it in a closed shadow tree, so it is clicked 30 pixels from the left
   edge). The widget has 8 seconds to report its answer.
3. **Solver.** Otherwise Anti-Captcha is asked for an answer token (`qorqut/browser/captcha_solver.py`: `createTask`,
   then `getTaskResult` every 3 seconds, 120 seconds at most). It gets the widget's type, its site key and the address of
   the document that holds it, without the query. The token is written to the widget's form fields, passed to the page's
   callback (`data-callback`, or for reCAPTCHA the one given to `grecaptcha.render`), and returned by the widget's
   `getResponse()`.
4. **reCAPTCHA v3** needs the action name the page sends, which only the page's own `grecaptcha.execute` call shows. The
   first `captcha` wraps that function and answers `again` ("send the form once more"); the second asks the solver with
   the action seen and leaves the token for the page's next request, once.
5. **Cloudflare's own page** gets the click and 25 seconds to give way. A token cannot pass it (its pass is a cookie tied
   to this browser's address), so the solver is not asked.

The command's output is one JSON line: `captcha` is `solved`, `not_found`, `again` or `failed`, with `type`, `method`
(`click`, `solver`, `already`, `waited`), a plain `reason` for a failure, and `next` when the agent has something to do
(for a failure: "Ask the owner."). When `next` leaves the captcha to the owner (a failure, or no captcha recognised) and the
tab is known, the reply also carries `reference`, the tab's `tab` reference (see [The tab-reference command](#the-tab-reference-command)),
and `next` says to pass it to `request_user_input` or give it to Ordubashy, so the owner is shown the tab instead of being told
where to look. Exit code 0 only for `solved`. The whole command is bounded at 150 seconds; an agent's tool call is given up
on after 240.

The key is the Global Settings variable `CAPTCHA_SOLVER_API_KEY`, read on the server for each call through the Settings
files' reader, the private values over the shared ones; `CAPTCHA_SOLVER_PROVIDER` may say `anticaptcha` and nothing else.
Without a key the click still works and the solver step fails with a reason that names the setting. The key and the
token appear in no reply, log line or exception; the solver's replies are reduced to its error code. The solver is
called over HTTPS only, ignoring proxy variables and refusing redirects.

Each attempt is one line in `operations/.runtime/browser-captcha.jsonl` (mode 0600, 1 MB, one older file kept): time,
calling agent, the site's host, captcha type, method, outcome, failure code, seconds, and the solver's charge when it
reported one. The same line goes to the service log.

Checked by `tests/test_browser_captcha.py` and `tests/test_browser_captcha_solver.py` with stand-ins for Chrome and the
solver, and by `scripts/check_browser_captcha.py` on a real headless Chrome with local pages that copy the widgets' frame
addresses and form fields and a local solver. No real widget and not the real solver have been run: whether a real
checkbox passes on a click from this headless Chrome, whether sites accept an inserted token, and the solver's task names
are unverified. Known limits: a callback passed to `hcaptcha.render` or `turnstile.render` in code cannot be reached (the
fields and `getResponse()` are still set); picture and text captchas of other vendors are not recognised; after a failed
click a vendor's picture puzzle may stay open over the page.

## The tab-reference command

When the owner must do something in a page (a captcha that could not be solved, a sign-in, a confirmation), the agent sends
`["tab-reference"]` as a `browser_turn` command, with nothing else, and shows that tab in Chat instead of describing where to
click. Like `captcha` it goes in a call of its own (inside `commands` it is refused before anything runs, as is any argument),
it is run by the server and not by `agent-browser` (`qorqut/browser/tab_reference.py`, dispatched in `access.py`), and the
shell launcher does not have it. It is read-only: it touches no page. It marks the session's tab as used
(`idle_tabs.note_use`), so a tab waiting for the owner's answer is not unloaded for idleness, and it takes no command lock.

It reads the tab the caller's session is bound to as `captcha` does, checks that tab is open in the browser, and prints one
JSON line with exit code 0: `{"reference": {"type": "tab", "id": "<agent uuid>:<tab id>"}, "next": "Pass this reference to
request_user_input, or give it to Ordubashy, to show the owner this tab in Chat."}`. The agent is the one whose tabs the
command ran in: the caller's, or a worker's when Ordubashy has selected that worker's tabs. With no tab
open (or a bound tab that has closed) it exits 1 with `{"reason": "..."}` telling the agent to open the page first; in a managed
desktop, which is no agent's browser, it exits 1 and says to use a `browser` reference.

`request_user_input` takes the reference as `{"type": "tab", "id": "<agent uuid>:<tab id>"}` with no `project_id`
(`qorqut/native_chat/references.py`). Naming a tab grants no control and no authorization:

- **When the tool is called** the agent must be one the caller may read (as for an `agent` reference) and the tab must be
  listed by that agent's browser now; anything else (unknown agent, browser stopped or not answering, tab closed) is the
  tool's usual "reference is not available".
- **When Chat is read** the same check is made again for each page of Chat, with the browser's tabs listed once per agent
  however many of its tabs the page names. The owner's card is `{type, id, project_id: null, label, available, agent_id,
  tab_id, agent_label}`; `label` is the page's title (at most 200 characters, else the address's host, else "Tab"). A tab that
  is gone shows the "Unavailable tab" placeholder. The title is the page's own text and is only ever shown as text.
- **Viewing** is the owner's alone and goes through the existing live-view route (`browser/live.py`); a reference neither
  opens a view nor lets anyone else.

Checked by `tests/test_browser_tab_reference.py`, `tests/test_chat_references.py` and `tests/test_user_input_tab.py`.

## Projects have no browsers

A Project has no browser, proxy, profile or isolated desktop: `project_config_*` accepts no `browser` section
(a section an older installation stored is kept inert and nothing reads it), and `browser_turn` takes no `project_id`.
Every browser is Global. An agent uses its own configured browser (see above and [browser management](BROWSER-MANAGEMENT.md)),
and the configured Ordubashy may name one of the managed Global desktops by id ([browser desktops](BROWSER-DESKTOPS.md)).
Naming a browser grants nothing: control is the ordinary `browser_turn` permission plus the selected browser-control skill,
rechecked on every call, and a handle is bound to the authenticated credential, machine registration and browser.

## Validation

`tests/test_browser_control.py` checks fail-closed configuration, override rejection,
session binding, environment isolation, timeout handling, empty-tab diagnosis,
selected-role projection, absence from startup/MCP configuration, and removal on
role change while preserving operator configuration.

`tests/test_browser_command_vocabulary.py` checks every row of the vocabulary above, every refusal and its advice, the
lifecycle options in every position of every command, and that `read` is answered from one batch. It needs no Chrome.
`tests/test_browser_frame_command.py` checks `frame`, the refusal sentences and the advice added to "Frame not found".

The opt-in real test launches and terminates only a disposable headless Chrome
profile on an ephemeral port. It attaches through the locked CLI, creates a test
page, interacts with it, preserves an existing tab and verifies Chrome survives
detachment:

```sh
QORQUT_TEST_WORKSPACE_ROOT=/absolute/path/to/workspace \
QORQUT_TEST_CHROME=/usr/bin/google-chrome-stable \
  /absolute/path/to/venv/bin/python -I -m pytest -q tests/test_browser_control.py
```

Owner conversational checks: “research this URL” must not attach or load the full
procedure; “use Chrome on qocaat to inspect this page” should load it and select
the configured target. Follow with unrelated web research to check that browser
permission is not carried forward. Automated source tests do not prove model
instruction-following behavior.
