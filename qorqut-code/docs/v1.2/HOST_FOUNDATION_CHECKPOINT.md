# Host foundation checkpoint: the retained host on the standalone Operations engine

This is a source checkpoint of the retained host on the standalone Operations engine. Evidence comes from isolated synthetic
instances only (temporary directories, a disposable virtual environment); no user instance, native agent, server, model/provider
call, deployment, package publication or live data was involved. It does not claim release readiness.

The sections below are cumulative; the first sections describe the original foundation. Later work moved Signoffs, routines,
background, quiescence and the neutral Context item/relationship/review machinery to the engine, added retained
Signoff/routine/background wiring through typed host ports, one service lifetime owner, the five neutral-item host obligations and
installed synthetic evidence (see "One service lifetime"). Component pins named below describe the earlier branch;
`HOST_FOUNDATION_SOURCE_RECEIPT.json` records the combined baseline.

### Transaction order inside one writing unit (the engine's)

body -> `ChangeFeed.capture(connection)` (reads pending `inbox_changes`; never raises) -> registered finalizers in registration order (`finalize_events`: turns captures into addressed inbox events and deletes them) -> `COMMIT` -> `ChangeFeed.publish_commit(...)` (once; never raises, never undoes the commit). A finalizer or record/file hook exception rolls the whole unit back, including the document row, shared-history version, receipt transition and every inbox row. Document availability follows the file receipt: `applying` -> file written atomically (`.bazarlyk-` temporary prefix) -> `applied`/`ready` plus shared history in the finalizing transaction, or `conflicted`/released. Acceptance case 4 proves each point with the real finalizer and feed.

### Schema ownership

The composed DDL is the committed target contribution `composition/schema_ddl.py`, never migrated and edited directly. (This checkpoint originally recorded a generator, `derive_host_schema.py`, that derived it from the numbered deployed-v1 SQL files and rendered an ownership ledger; the generator, the ledger and those SQL files were retired in v1.3.) Two repository specifications were corrected while validating against the engine: `system_incidents` and `broadcast_deliveries` declare `revision_column=None`, because the deployed v1 tables have no revision column (the engine's compile step requires declared columns to exist).

## Paths and callers

`InstancePaths` is the only location source. `Runtime.root == paths.operations`; the database is exactly `paths.database` and is *opened and validated* (`open_database`), never created or converted by the service, `build_runtime` or any host command; `initialize_empty_target` is the explicit entry point for isolated synthetic setup. `initialize`/`open` refuse a store of another identity, a pre-target v1 store or a symlinked path without writing.

Resolution rules (`composition/locations.py`):

- a business is its registered `slug` as folder: `operations/businesses/{slug}/{hq,code}`; a global agent `operations/agents/{id}`; a business agent `operations/businesses/{slug}/agents/{id}`. Agent workspaces are identity-based everywhere (no name-based helper remains); display names, tags, role names and the stored `workspace`/`hq_path` columns never select a location, and `AgentConfigResolver.profile` rejects a stored workspace that differs from the derived one (`registration_conflict`);
- a document path's first segment alone chooses between a business `hq` and the scope root holding `agents/` (global documents are relative to `operations`); traversal, absolute, backslash and symlinked paths are refused by the engine's `RegisteredFileTarget.resolve`, and a symlinked business or agent folder is refused by `InstancePaths`;
- no older root, process-wide root default or working-directory fallback is probed; `BIZ_ROOT`/`--root`/`--businesses-root` selections are gone from the retargeted consumers.

Runtime metadata that lived at the old root now lives under `paths.runtime` (`operations/.runtime/`): `browsers`, `secrets/browser-proxy`, `secrets/browser-desktop`, `sandboxes`, `sandbox-host.json`, `preview-host.json`, `browser-surfaces.json`, `browser-turns`, `inbox-paste`, `reports/daily`, `business-backups`, `backups`, `maintenance`, `browser-session.key`, `artifacts`, `locks`, and the old ContextBase data directory at `.runtime/contextbase` (distinct from the new Context's `.runtime/context`).

Caller changes (signatures now take `paths`/`InstancePaths`, not a root): `build_runtime(workspace, *, paths, database=None, ...)` and `assemble(workspace, *, paths, ...)`; `register_context_sources(database, paths, *, template_root, business_id=None, hq=None)`; `apply_initial_plan(..., locks)` and `FileApplier(database, resolve_target, *, locks)` (locks are mandatory); `FullRecoveryStore(database, paths, *, repository, ...)` with `RUNTIME_RELATIVES` under `.runtime/`; `RecoveryAdminConfig.load(path, *, paths)` (config key `operations_root`; the GitHub-app config key `businesses_root` -> `operations_root`); browser (`credentials_directory`, `serve(database, paths, ...)`, provisioning and isolated-deployment helpers, the access lease/turn store), `TableOperations(database, paths)`/`TableHistory(database, paths)`, sandbox config/service/terminal/lifecycle/preview/readiness/runtime, transport auth/terminals/http, reports, background, file viewer, inbox paste, content sessions, ContextBase, bootstrap preparation/seed/migration/owner-prepare, global chat. CLIs use `--instance-root` and repeated `--component NAME=ABS` (`bazarlyk/service/instance_arguments.py`).

Decisions made while retargeting (none changes v1 authority or semantics): identity-based workspaces everywhere; runtime metadata under `paths.runtime`; global environment file at `operations/.env`; the Docker installation identity is the hash of `paths.operations`; an isolated browser deployment's `root` is its instance root; the recovery-admin config key is `operations_root`.

## Dashboard launcher (`biz-dashboard`, branch `v1.2/application-host`)

`start.sh` builds `python -I -u -m bazarlyk.service --workspace W --instance-root R --component NAME=PATH ... --host H --port P` only from the private config's `INTERPRETER` (or `BIZ_DASH_PYTHON`), `WORKSPACE` (or `BIZ_DASH_WORKSPACE`), `INSTANCE_ROOT` and `COMPONENT_*`; a stable `BIZ_DASH_LAUNCHER` receives the same selection without an interpreter. Only the host launcher, example config, README and launcher tests changed; no frontend or style files.

## One service lifetime

(The Start and Stop bullets below are the foundation checkpoint's; `RUNTIME_LIFETIME.md` is the current contract.)

`bazarlyk/service/lifetime.py` (`ServiceStep`, `ServiceLifetime`, `ShutdownReport`, `ShutdownIncomplete`); `Runtime.lifetime()/start()/stop()` are the only entry points and delegate to it.

- **Start:** validate the stored target and maintenance state (`validate_target`: `open_existing` + `require_authority`), expire browser turns and reconcile prepared file effects, then start the retained services in the fixed order `global_chat, activity, incidents, signoffs, background, terminal_control, content_sessions, telegram, broadcast_dispatcher, sandbox, previews, recovery_admin, email_history, outreach_registrations, changes`. A service that is not installed in this composition is recorded with its reason (`inventory()`), an installed-but-disabled one (content sessions) is started and does nothing. A failing start stops exactly the services *that attempt* started, newest first, including the failing one (it may have begun a thread before raising); a service an earlier completed attempt left running is neither started again nor unwound; the original exception is never replaced by an unwinding failure and the database stays open.
- **Stop:** every installed service is asked to drain in the retained order (`content_sessions, global_chat, terminal_control, telegram, broadcast_dispatcher, activity, incidents, changes, outreach_registrations, recovery_admin, previews, sandbox, background, signoffs, email_history`), then write admission is closed and its already admitted writers are awaited (5 s), then SQLite is closed. A service that raises, including `TimeoutError`, or an admitted writer that does not drain makes the shutdown **incomplete**: the remaining services are still stopped, the database is *not* closed, admission stays closed, and `ShutdownIncomplete` carries the `ShutdownReport`. A retry after the cause is gone completes and closes SQLite.
- **A normal return is proof of the drain.** After its bounded join a service's stop method must raise `TimeoutError` if its thread survived, and keep the thread reference until the thread has ended (the next stop can then prove the eventual drain). Review found six wired stop methods that returned after a timed join regardless: `TerminalChat.stop_observer`, `AgentActivity.stop`, `IncidentDrain.stop` and `ChangeFeed.stop` (the last two also discarded the reference), `TerminalControl.stop` and `BroadcastDispatcher.stop`; each now raises and retains its thread, with no other change. `ChangeFeed.start_external_writer_ticker` treats a retained thread that has ended as absent (a live one still prevents a second ticker). The rest of the finite wired list was read and already raises on a survivor and retains its thread: engine `SignoffService.stop` and `BackgroundService.stop`, `ContentSessions.stop` (and its workers), `TelegramBridge.stop`, `BusinessSandboxService.stop` (worker and listeners), `BusinessPreviews.stop` (and the browser viewers), `RecoveryAdministration.stop`, `EmailHistoryOutbox.stop`, `OutreachRegistrations.stop`.
- Native product sessions are not owned here: `global_chat` is asked only for `stop_observer`, and no service call resets, kills or reattaches a native session.
