# Context composition and active-engine retirement

The original Context contribution is preserved in the history of `v1.2/context-finish` and combined with the accepted runtime ownership and recovery contributions. The source receipt records the exact engine pins.

## What the stock host composes

* **Storage.** `composition/schema.py` `record_contributions()` carries `context_queue`, `context_filing` (source versions, filings, completions, source bindings), `context_graph_edits` and `context_usage`, one contribution per owner, so a stock instance has every table the queue, filing, edit and usage paths need. A custom assembly that omits one is refused at admission with `composition_error`, not half-working.
* **One queue, composed before the domains** (`bazarlyk/shared_context/service.py`, `compose_context`): `FilingOutcomes`, `ExecutionFacts`, the single `ContextQueueOperations`, the `FilingPorts` and `GraphEdits` over it, and one `Context`/`Pipeline` over `InstancePaths.context` and `InstancePaths.context_runtime`. `build_runtime(..., context=ContextSettings)` passes them to `register_business_domains(filing=, graph_edits=, queue=)`. The domain factory, the filing ports and the lifecycle owner hold the very same objects. Composition writes nothing, creates no repository, principal, thread or provider run (`Context(...)` is inert; the host never calls `Context.initialize`).
* **Settings.** `ContextSettings(runner, config, clock, poll_seconds, max_backoff_seconds, usage_page_size, usage_max_pages)`. The injected runner and the library `RunnerConfig` must agree; without either the library defaults and its normal adapter apply. `service/main.py` accepts an explicit `--context-config` JSON file (`runner_config_from_file`: absolute regular file, bounded, only `RunnerConfig` field names); nothing is read from a business, the environment or an old default. `service/main.py` no longer assigns `context_base_path` or builds the old service.

## Lifecycle contract (`runtime.context_services`)

`ContextServices` is inert after `build_runtime`. Its contract, for the host lifetime that owns the instance:

* `start()` registers (or verifies) the dedicated backend `system` principal `uuid5(NAMESPACE_URL, "qorqut-v1.2:" + installation_id + ":context-driver")`. An existing row of another kind, or a disabled one, is a visible `invalid_principal` conflict and is never repurposed or re-enabled. It then runs the existing `ContextQueueDriver` through the existing `ContextDriverLoop` on its one thread, with the bounded synchronous `ContextUsageCollector` (lock `paths.locks/context-usage.lock`) before and after each step.
* `stop(timeout=…)` returns `{stopped, in_flight}`; `stopped` is true exactly when that thread, with any in-flight draft, Git publication, SQLite recording or usage page, has ended. `running`, `wake()` and `diagnostics()` complete the fixed surface. A change-feed listener (`ChangeFeed.add_listener`) wakes the loop after any commit except the driver's own `context_queue_driver*` operations.
* No Ordubashy is created (`configured_ordubashy(..., require_codex=False)`). A missing, inactive or unregistered coordinator blocks only Context progress (`not_ready` / `no_coordinator`): ordinary operations, uploads and queued inputs continue. A missing or uninitialized Context is never initialized by the host: the step answers `not_ready`, no input is blocked for a repository that was never there, and inputs stay queued until an operator explicitly initializes the Context.
* Lane A owns when `start()`/`stop()` run (after instance ownership; as a recovery-quiescence drain participant) and the nudge construction; this lane owns only what they call.

## Paths

`InstancePaths.context` is `operations/context-graph` (the one published, engine-owned Git root); `operations/.runtime/context` stays the runtime. Global authored Context sources (`context/_inbox`, `_people`, `_dumps`, `_maps`) stay under `operations/context/` with their existing scoped access. `composition/locations.py` `reserve_graph_root` makes `document_root` refuse a Global path whose first segment is `context-graph` (`forbidden`), and `document_path_at_global` never reports it, so a managed document can neither be registered into nor discovered inside the graph checkout. A business HQ path with the same name is unaffected. There is no old-path fallback, symlink or data move; the graph does not appear in generic authored snapshots by this change (later lanes decide capture).

## Retired (the active old engine)

Removed, with no compatibility shim: `bazarlyk/domains/contextbase/{__init__,service}.py` (`ContextBaseService`, `domains.context_base`, `runtime.context_base`, `ideas.context_base`); the `operations.py` there became `domains/context_sources.py` (`ContextSourceOperations`: `context_filings`, `context_upload_map`, `context_instruct`, `context_edit`, with `INSTRUCT_ROLES` unchanged); `seed_business`/`bootstrap_bodies` in the former Idea conversion (business creation now lives in `domains/business_creation`; Ideas are removed); the old-base projection in platform delivery; the `contextbase` git dependency (`qorqut-contextbase`) in `pyproject.toml`, `service-constraints.txt`, `tools/installed_host_probe.py` and the install docs (the `contextbase` extra name remains, pinning only `qorqut_learning`); `CONTEXT_BASE_READS` is `SHARED_CONTEXT_READS`. Old-engine tests removed: `test_context_base.py`, `_review`, `_legacy_adapters`, `_aliases`, `test_context_retrieval.py`, `global_filing_costs_browser_fixture.py`.

## Callers retargeted

* **Business readiness** (`business_setup.context_exists`) reads the published graph through `PublishedPresence(reader)`; a missing Context answers "not present". No second store.
* **Platform delivery writeback** (`platform_actions/delivery.py`) records the actual outcome through the accepted Action path only; no direct graph write, no second external operation, no model. The Action revision reaches the Context through the queue in its own order.
* **Business creation** (`business_create`) files the founding material automatically (next section). **Business setup** uses the graph reader and the ordinary filing path only.

## Founding upload (`domains/business_creation/filing.py`)

`business_create` freezes, in the same Global plan, exactly one business-owned `context_upload` snapshot of the new business: frozen UUID, path `context/_inbox/<prepared-date>-<uuid>.md`, body = the frozen `context/founding.md` (deterministically composed from the submitted name, slug, summary, the owner's confirmation, the accepted source references by identity, revision and hash, and the owner's product, ICP, brand and positioning in that fixed order), nothing else. Metadata and references are bound to the hash of that frozen brief, to the accepted source snapshots and to the founding/core document IDs the same plan creates; attribution and the job's initiator are the original caller, never the approving owner.

* `prepare` obtains the registered `context.file` program, its current definition and its active system worker through the installed program authority (business scope supported; the worker must be in the same creation payload's planned memberships), rebinds the Global job-value result to the new `business_id`/`target_namespace`, and runs `context_filing.admit` on a private child builder scoped to the future business. The child never reaches policy or `allowed_business_ids`; only its four frozen row values (job, source version, filing, queue input) are carried inside the `create_business` change. The envelope and its size limit are validated (`source_too_large`) before the plan is returned. `require_worker`, admission and the transaction model are unchanged; no temporary business, no fabricated system caller.
* `verify` (at validation and again at application, on the round-tripped canonical plan) recomputes every value from the frozen documents, file effects and the Operations primitives (`general_arguments`, `general_values`, `envelope`) and refuses anything else: another body, reference, scope, digest, revision, attribution, definition, worker, additional record kind, a second upload, or an existing business, source or job. `apply` inserts the four rows in an ordinary upload's order after the business, documents and worker memberships, in the existing short transaction, through the normal record hooks. The file-target allowlist gained exactly the `context/_inbox/<date>-<uuid>.md` pattern, bound to that one document by `verify`.
* The review text says plainly that the founding material is queued, not published, and stays pending until a verified publication and completion. Nothing is published at creation; there is no provider call, graph write, second transaction, scheduler, duplicate queue or new job type. A missing or uninitialized Context, or an earlier blocked input, leaves the creation and a pending filing. A later edit cannot replace the frozen input; the document then reads unfiled/pending for its own current text.
* **Base defect fixed on the way** (`creation.py` `file_target`, formerly `conversion.py`): the creation file targets were rooted at the not-yet-existing business HQ, so `RegisteredFileTarget.resolve()` raised `FileNotFoundError` for every business creation on the integrated host. They are now rooted at the operations root and addressed by the location resolver's operations-relative path (as the v1 creation always was). Without it no business could be created, with or without the upload.
* The template's `context/INDEX.md` inventory is the seeded scaffold and does not list the founding upload until the next ordinary upload regenerates it.

## Checks and what they prove

The stock host, real Context Git store and pipeline, deterministic injected model runner and synthetic records passed 55 focused checks across `test_host_context_services.py`, `test_host_founding_upload.py` and `test_context_completion_acceptance.py`. This includes automatic founding filing, source edits, blocking, completion and queue ordering. No provider or original data was used.

The runtime now owns Context start/drain/resume; recovery includes both graph authority and runtime; nightly capture is bound by the host. The retained campaign feed uses Tasks/Actions. Obsolete single-agent conversion/history-baseline commands and the old Context extra were removed. The final role sources are validated directly without test-time permission edits. Schema artifacts and source pins are refreshed in the combined checkpoint. Installed-package and migration evidence are separate from these source checks.
